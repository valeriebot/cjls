# `calca` — incremental computation

The incremental computation engine the frontend is built on: inputs, interned values and tracked functions, recomputed only when what they read changed. No project dependencies. Two packages: `calca`, the runtime, and `calca.macros`, the macros that are its API; a user imports both.

Every macro is `Calca`-prefixed:

```cangjie
@CalcaInput
public struct SourceFile {
  public let path: String   // a getter only
  public var text: String   // a getter and a setter
}

@CalcaInterned
public struct Name {
  public let text: String   // fields are `let`: they are the identity
}

@CalcaTracked
public func lineCount(db: Db, file: SourceFile): Int64 { file.text(db).split("\n").size }

let file = SourceFile(db, "a.cj", "…")
file.text(db)
file.setText(db).to("…")                           // .withDurability(Durability.High).to(…)
Name(db, "x") == Name(db, "x")                     // one Id
```

- **A database** is the user's interface over `Database` and a class implementing it with a `prop storage: Storage` — a prop, since a `let` cannot implement an interface's. A `Storage` is one *handle*, used from one thread at a time: `Storage()` makes a database and its root handle, which reads the current revision and is the only one that changes inputs; `storage.snapshot()` gives another thread a handle pinned to the revision current then, and the class wraps that in a `snapshot()` of its own type.
- **Writes wait for operations, not for handles**, not for every live snapshot to be dropped, because Cangjie has no deterministic destruction: `~init` runs only once the GC collects, which without allocation pressure is never, and a snapshot escapes any lexical scope. Every operation outside a query (a tracked call, a field read, an input created, a value interned) goes through the gate in `Runtime`, counted in flight, released in `finally`; nested ones only check. The count is an atomic a reader adds itself to before it looks for a pending write, as a write marks itself pending before it looks at the count: one of the two sees the other, and a reader takes a lock only to wake the write it held up — not the gate, which the write holds through its change, so a snapshot meeting a write throws `CancelledException` at once (`ParallelFetchBench`: ~7% of a hit). A write cancels what is in flight (the next calca call there throws `CancelledException`), waits for the count to drop to zero, and opens a new revision holding the gate. A snapshot used after that throws it too, so one answer never mixes revisions, and there is nothing to close: a forgotten snapshot holds up nothing. A write — setting an input, or creating one — from a snapshot or from inside a query is an `IllegalStateException`; creating one opens no revision, since nothing computed can have read it — except a singleton (`@CalcaInput[singleton]`: at most one row, `Config.get(db)` / `tryGet(db)`), which a query may have looked for: `get` and `tryGet` record a read of the table, and creating the row is a write of its own. `storage.batch { … }` makes every set and create inside it one revision, cancelling and draining once (`AnalysisDatabase.applyChanges` goes through it); nothing is read inside a batch, since a memo computed there would be current in a revision the rest of the batch still changes. A long computation of one's own calls `db.unwindIfCancelled()`, or the write waits for it.
- **The engine** is red-green: a memo records what it read, is reused when nothing did change (checked cheaply by `Durability` first, then dependency by dependency, which may execute those), and a value computed again equal to the old one keeps its old `changedAt` (backdating), so what read it does not run again — hence `@CalcaTracked` results are `Equatable`, unless `@CalcaTracked[noEq]`. A function needing its own value is a cycle, including when it is only found while verifying (whoever verifies the key executes it instead, which finds it). `@CalcaTracked[cycleResult: f]` recovers: when every query executing on the cycle has a fallback, each is marked, depends on the union of what they all read (minus themselves), unwinds at its next read (`CycleUnwindException`) and takes its fallback; otherwise it is a `CycleException`, `participants` naming the queries. A cycle across handles recovers the same way (D35): the handle that would close the loop gives way (`GiveWayException`), unwinding to its query the loop waits for and letting go of it; the owner computes the whole cycle on its handle, and the one that gave way fetches again what it left. A body catching one of these exceptions (`catch (e: Exception)` around a fetch) does not stop it (D41, A21): the exception marks every query it unwinds (`ActiveQuery.unwoundBy`), and a marked one whose body returns stores nothing and throws it again.
- **Interned values** are collected once unused (D18). The table is a `Slab` of the fields, as a generated `CalcaFields_<Name>` struct (a tuple cannot be `Hashable`), with a `HashMap` from fields to `Id`; an `Id` is a slot's index and its generation, 32 bits each, so a collected value's `Id` never finds the one reusing its slot, and reading it throws. Interning records a dependency, `changedAt` now, with the interning query's own durability so far; reading records none. Only values interned by `Low` queries go (outside a query they are `High`), once unused for `revisions: N` active revisions of their table (3 by default; `@CalcaInterned[forever]` keeps them, and records nothing), collected in `newRevision` under the write gate. A tracked function of several arguments is keyed by them as one generated `CalcaFields_<function>_S<type>…` (of one, by the argument itself; of none, by `Unit`); what it generates is named after its parameter types too (`mangled`: `_S` before each type, `_` doubled, signs a letter), a method's after `Type.method`, so overloads are queries of their own, and a method never meets a function. A tracked function's keys are a `Slab` too; a memo goes with any interned value its key is or holds: the interned struct implements `InternedValue`, a function's `CalcaFields_…` `InternedFields` (each field through `calcaKeyOf`, a cast at run time, since a macro sees only tokens); the first key tells which, and the table registers with every interned table a key's values come from, which tells it what it collects (`dropKeys`).
- **Tracked methods**: `@CalcaTracked` on an `extend` of an input or interned type makes a query of each method marked `@CalcaTracked` in it (options on its own mark), keyed by `this` and the arguments — a `static` one by the arguments alone; the body stays a member (`calcaBody_<name>`) for `this` and the type's other members, the holders go after the `extend`, since an `extend` holds no variables or types. The inner mark sees its parent (`insideParentContext`) and only sends the method's name and options; the outer one also gets a message without a name, skipped. `@CalcaTracked` on a method of a plain `extend` cannot work: a member's macro emits no top-level holder.
- **Generated code** keeps one process-wide descriptor per input type, interned type and tracked function in a static (`InputIngredient`, `InternedIngredient`, `TrackedFunction`), holding an ingredient index reserved at initialization; each database creates the matching per-database state lazily at that index. The body of a tracked function goes to `fetch` with every call, as the holder's type (`fetch<B>`, `B <: TrackedBody`, a `static func calcaExecute`), never into the static — see the static-initialization rule under macro mechanics — nor as a closure, which every call would allocate.
- **One computation per memo** (D29, D35): the handle verifying or computing a memo claims its key; another one waits for the claim, then takes what the owner left. A memo verified in the current revision is read without a claim, and without the table's lock (C9): entries are found by key in a `ConcurrentHashMap`, the memo in an atomic reference; only an `lru` function's hit locks, to record its use. A waiter looks every 10 ms whether it was asked to stop; `Runtime.waitsFor` finds a wait that would close a loop across handles; a waiter waking records nothing again, or it would find a loop being given way.
- **LRU** (D17, D36): `@CalcaTracked[lru: N]` keeps the values of the `N` keys fetched last, their order an `IdLru`: a linked list over the keys' dense `Id`s, nothing hashed, so a touch is cheap; but it is made under the table's lock, which a hit without `lru` does not take: ~13 ns more per hit, a third more (`LruFetchBench`). Eviction goes with the touch, under that lock, within a revision too (D36): a question over every file holds `N` values, not one per file; a reader keeps a value it was handed, and one fetched again in the revision it was evicted in is computed again with its `changedAt`. `newRevision` trims what a fetch that did not end left; an evicted memo keeps its revisions and dependencies, is verified by its edges without executing, and is computed again only when fetched. After its inputs changed it cannot backdate: there is no old value to compare with.
- **Not there yet:** tracked structs, accumulators, dropping memo keys that are not interned values (#14).
